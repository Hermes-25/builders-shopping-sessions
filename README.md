# Shopping Sessions

A native Rust implementation of the Databricks Shopping Sessions track. Build with `docker build --platform linux/amd64 -t shopping-sessions .`. The binary reads `DATA_DIR` (default `/data`), writes `OUTPUT_DIR` (default `/output`), and uses `NCPU` worker threads (default eight).

## Pipeline

1. Assign each worker a nominal two-MiB CSV window. The worker reads its boundaries on demand and decodes exactly the records whose first byte is in that window, extending its mapping for a long record. Short ASCII identifiers have a reversible 63-bit representation. The dictionary owns the bytes of longer, multibyte and NUL-containing identifiers, so each input mapping can be released immediately.
2. Detect delimiters and quote boundaries with AVX2 and BMI2 when available. For short rows the scanner selects each field boundary directly from the delimiter mask. Event rows with at least three separators in both the leading and trailing 64 bytes can select their first and last three delimiters independently. It checks every row’s complete field count and matching quote edges. Longer records and other processors use the general parsers. A calendar index verifies the complete date prefix before using a cached reporting-window date.
3. Build linked identity components in parallel. Each union chooses the byte-wise smallest name as its root. Each worker computes a reversible permutation of the full event ID once and uses it to count and partition its input, buffering eight rows per destination. The 24-byte row holds that full key, the raw user ID and a payload. Purchases and values outside the inline timestamp range use an exact source-local side table. Within each partition, an eight-byte index points into a dense vector of winning rows. A generation number distinguishes the active partition, and a short fingerprint screens candidate matches before the full key comparison. Even invalid rows participate in the earliest-ingestion decision. Each worker then scans only populated winners and routes valid visits through the raw user's identity shard to their canonical people.
4. Count events and clicks by integer person slot and scatter them into contiguous timelines. Where the duration and category bounds permit, each visit occupies eight bytes and each click occupies sixteen. Wider values use full-width fields. Sort each person's visits and clicks, scan session gaps, and maintain the inclusive seven-day attribution window. On long timelines, record each campaign’s range of assisted session indices and add the count when its range expires or its reporting day ends. Short timelines tally active campaigns directly.
5. Accumulate campaign/day totals per worker. A sparse representation handles unusually large date or campaign ranges. Write independent user Parquet partitions with row groups of up to 65,536 rows. Numeric columns use little-endian values. Repeated user names and small category dictionaries use Parquet’s hybrid RLE/bit-packing encoding. User columns with few repeated names and large category dictionaries use plain strings. A standard Parquet writer emits the merged campaign table.

For each supplied product and campaign catalog, the loader looks for a shared prefix with closely spaced canonical decimal suffixes. An exact integer array serves that part of the catalog, while the byte-key dictionary retains all other spellings. The catalog itself determines the prefix and number range.

Dependencies are pinned in Cargo.lock and include Apache Parquet, Rayon, memchr, memmap2, rustc-hash, and serde_json. All contest-specific processing code was written for this entry. The official generator, fixtures and expected tables are used for local verification.

The Docker build generates a synthetic clickstream with `tools/profile_input.rs` and runs an instrumented solver on it. The Rust compiler uses the resulting branch counts to build the production executable. The runtime image contains the executable and Debian base.
